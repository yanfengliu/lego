### /root/native_cleanup_review

#### The proposed cleanup addresses the observed leak

The retained a2 assignment receipt, SHA-256 `793e7162c2248b1e7b3656473ae7125d6660db71bc6770fed0b43458dedf4993`, records real native assignment error 6, zero resume calls, both original handles closed, and a nonsignaled retained child both immediately before original process-handle close and after the method returned through `finally`. Separate observer rescue then confirmed exit 27185. Its summary at `2bbb912a1a9a58f2921f982f8d8808bb630d97e0de7b82007ce37e7464215aa7` reports product failure. These are actual historical receipts; this review did not rerun them. Original and adapted normal receipts both record exit 37, total 2, active 0. The value 2 is an observed accounting result, not a replacement global invariant.

In `source-proposed.cs:361-369`, the existing job termination remains first and a failure is collected rather than skipping direct-child cleanup. Every ordinary managed exit from the launch body after `processCreated = true` reaches `ConfirmCreatedProcessExit` using the original process handle. This includes assignment refusal before resume. The helper at lines 227-241 checks for an already signaled child, otherwise terminates that exact handle and waits up to 5000 ms. Only a signaled wait establishes exit. Original thread and process handles are not closed until lines 390-391, after that check. The observer does not supply this product operation.

The helper correctly accepts a signaled final wait even when termination returned failure, since a racing exit can make a termination call fail. Microsoft's [TerminateProcess contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess) says external termination is asynchronous and that an already terminated process can return access denied; its [WaitForSingleObject contract](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject) defines the signaled and timeout results and requires keeping the handle open during a pending wait. The candidate follows that order. It does not equate termination-call success with observed exit.

The four declared edits leave the original launch body, `Require`, timeout behavior, writer-start order, exit query, job query, accounting loop and refusal predicates unchanged. The new helper is local to this launcher. The normal path adds an exit check after the launch body has already observed child exit, so it should not terminate a normally completed child. Actual compiled normal parity remains an execution requirement.

#### Error retention and unresolved ownership are accurately bounded

The catch at lines 351-355 captures the original exception and rethrows it. With successful cleanup, the original type, native error, message and stack are retained by that rethrow. With cleanup failure, the aggregate at lines 398-403 places the original exception first and retains collected cleanup exceptions. Direct-child, writer/event and final-handle cleanup stages are separated so an ordinary caught exception in one does not skip later attempts. The unresolved-exit message records initial wait, termination result and native error, and final wait and native error. The final handle-close helpers retain operation labels and native errors. This changes the failure surface only when cleanup itself reports failure; it does not replace the original launch error with an unrelated cleanup error.

This is not an ownership-transfer mechanism. If native termination or waiting cannot establish exit, the candidate reports uncertainty and still attempts to close its original handles. When those closes succeed, no exact process handle remains with this caller or is exported in the aggregate. After failed assignment, the private job does not contain that child. A remaining live child therefore is possible on this explicitly unresolved path. The README describes that limitation and leaves caller stop behavior outside the packet. I do not treat this disclosed limit as a source-level blocker to the bounded synthetic experiment, whose repaired assignment arm requires confirmed exit and cannot pass on uncertainty. I also do not treat a later successful arm as proof of cleanup under all OS failures or of production caller enforcement. An actual unresolved cleanup result must stop the experiment before another child; source or production promotion must separately assess the caller contract it intends to claim.

The unchanged writer cleanup still ignores its final `Join` result and includes unchecked native writer cancellation/close calls. The old pre-thread-start stream-ownership issues are not settled by this edit. The design explicitly excludes those cases and does not claim the six controls exercise them. I found no additional material defect in the proposed change within its stated claim. These existing limitations remain outside this review's acceptance rather than silently becoming repaired behavior.
