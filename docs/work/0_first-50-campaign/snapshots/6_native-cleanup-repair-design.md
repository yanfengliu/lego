## Product change

After successful CreateProcess, `finally` checks the original held process handle on every ordinary managed return or exception path. A signaled process needs no termination. Otherwise the candidate calls TerminateProcess on that exact handle and waits up to 5000 ms before either original child handle is closed. A successful wait is the exit evidence. A failed TerminateProcess followed by a signaled wait is accepted because the process may have exited between calls. Microsoft documents that external termination is asynchronous and a process wait is needed to establish completion; an already exited process can make termination fail with access denied. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

The existing job termination still runs first. Its failure cannot skip direct-child cleanup. Writer/event cleanup failure cannot skip original process/thread close attempts. Final native handle closes are checked individually. The original launch body, its call order, Require implementation, timeout path, and job/accounting refusal conditions are unchanged. Two local cleanup helpers keep this addition within the existing launcher; no supervisor or general process framework is added.

If cleanup succeeds, the original exception is rethrown with its type, native code, message, and stack intact. If cleanup fails, an AggregateException retains the original exception as its first inner exception and includes the cleanup errors, with operation labels or termination/wait results. This is a deliberate failure-surface change only when cleanup itself fails; it prevents cleanup errors from silently replacing the original failure. [AggregateException](https://learn.microsoft.com/en-us/dotnet/api/system.aggregateexception?view=netframework-4.8.1).

The source path analysis covers assignment refusal; ResumeThread failure after assignment; pipe/stream/event/thread setup errors after creation; input write errors; child wait timeout/failure; writer quiescence errors; exit-query failure; job-query/accounting refusal; and a normal return. Each reaches the same exact-child exit check while the created process handle is still held. An already exited child makes the extra zero wait succeed. Failures before successful creation have no created-child cleanup obligation.

## Exact unresolved boundary

If TerminateProcess fails or the 5000 ms wait cannot confirm exit, the candidate reports uncertainty and still attempts to release its original handles. A successful close then relinquishes this caller's process ownership; no exact process handle is exported in the AggregateException. If assignment had failed, its private job cannot establish containment of that child. The native child may remain alive, and this candidate does not claim otherwise. In the regression fixture the separate duplicate supports local rescue after the frozen product observation; the production caller has no such duplicate. The caller must treat unresolved cleanup as a stop condition. Enforcing that caller behavior is outside this packet.

The six controls below do not inject TerminateProcess failure, WAIT_FAILED, cleanup wait timeout, CloseHandle failure, or writer cleanup failure. They do not prove those error-reporting branches or all OS failure closure. The unchanged writer block still ignores its final Join result, and does not settle every pre-thread-start stream ownership issue. Catastrophic CLR failure, asynchronous worker death, kernel or driver noncompletion, machine suspension, and descendants after worker hang remain outside the local observation guarantee. A 5000 ms Windows wait is a finite API timeout, not a promise that all possible host failures end within five seconds of wall time.
