# Devlog — 2026-08-07

A single-unit session on the `--check` gates' error messages, taken as a class rather than as the one instance that was reported.

## A byte comparison reported as a moved hash

**Timestamp:** 2026-08-07 11:40–13:40

**Action:** `scripts/update-generation-pin.mjs` decided staleness with `previous === expected` over whole formatted bytes and reported it as a moved `populationDigest`. Split the reporting from the comparison: a new `scripts/generated-file-staleness.mjs` holds `describeTextDifference` plus one describer per gate, and the three gates — `pin:check`, `notices:check`, `schema:check` — call into it.

**Result:** The reported failure, reproduced by changing one comment character in `run-pin.generated.ts`, went from

```
Deterministic run pin is stale: run-pin.generated.ts holds sha256:366fefbf… but this build produces sha256:366fefbf…
```

to naming the axis it failed on: `stale in its file bytes only`, the line that differs, and all three pinned values stated once as already matching. Four axes now report separately — a pinned value moved, only the bytes moved, the file has no readable value of that name, the file does not exist — where one sentence covered all four.

**Reasoning:** The obvious fix is to compare the three pinned values instead of the bytes. That is wrong: the byte comparison is the only one that catches a hand-edited comment, a stray import, or a formatting drift that the format gate would then fail on separately. The comparison belongs at the byte level and the message belonged one altitude above it, asserting a cause the comparison cannot see. So the comparison stayed and the message moved down to what it can actually prove.

The same defect was already written out at length in `.gitattributes` — "the check is comparing file bytes while its message talks about hashes, so the error argues against its own verdict" — as commentary on a CRLF incident. Naming it there fixed the trigger and left the class, which is why it was still reproducible after the `-text` attributes landed.

**Validation:** 19 tests in `scripts/generated-file-staleness.test.mjs`. The load-bearing one is "never prints one pinned value as both held and produced", which fails against the old message for both a CRLF file and a reworded header. Each gate was also driven end to end against a perturbed working tree — comment byte, CRLF translation, moved digest, moved catalog, deleted file, dropped dependency row, relicensed row, renamed export — and the tree restored after each.

What the tests do not cover: the gates themselves are still thin wrappers that read files and print, and nothing asserts that a fourth `--check` gate added later uses this module.

**Code reviewer comments:** None — no independent pass was run, and the fleet's own rule scopes the multi-CLI review to persistence, security, concurrency, money, supply chain and sibling-repo work, none of which this touches. Two defects were caught by self-review rather than by the reported symptom: the write path's final branch claimed "the deterministic path itself changed" whenever the catalog hash held still, which fires when nothing but the bytes moved; and the notices gate reported any read failure as a missing file, so `EACCES` would have printed "does not exist".

**Notes:** `npm run verify` failed four times on this machine with no defect behind any of it, every failure a wall-clock timeout. Once with 47 across 18 files while four `claude` processes and two vendor services held the CPU — shell startup alone was taking over two minutes — and three times with exactly one, `apps/companion/src/test-run-recorder.test.ts`, whose first test does real ledger and CAS I/O against the 5s default.

What separates a pass from a failure here is not the tree, it is how the command is run. Backgrounded, that one file needed 8.5s and crossed; in the foreground the whole suite finishes in 24.09s and the file needs 3.6s. So a red backgrounded `verify` on this machine is not evidence about the change, and the way to get a verdict is to run the stages in the foreground in the gate's own order.

Attribution mattered because this session adds a test file to the pool, which could plausibly tip a borderline suite. It does not: at full parallelism the suite passes 148/148 with the file held out and 149/149 (1476 tests) with it in, back to back, in the conditions that had just failed. The browser suite flaked once the same way, on an event-loop-gap assertion measuring 257.7ms against a 200ms ceiling; that spec runs in 4.6s on its own and the suite passed 34/34 on a second run.

The worktree also had no `node_modules` of its own, so every bare specifier resolved up into the parent repository's — where `ajv` is 6.15.0 and has no `dist/standalone`. `npm run schema:check` therefore failed with `ERR_MODULE_NOT_FOUND` naming a path outside the worktree, which reads as a broken script rather than an uninstalled tree. `npm ci` in the worktree fixed it in 6s. Worth knowing before diagnosing a gate that fails only here: check whether the module it cannot find resolves inside the worktree at all.
