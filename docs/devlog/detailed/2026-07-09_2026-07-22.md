## Scoped patch policy shipped with three bypasses and was fixed 72 minutes later

**Timestamp:** 2026-07-09 / 2026-07-10

**Action:** `9b19cbe` (23:25) split 272 lines out of `compiler.ts` into `packages/brick-kernel/src/patch-policy.ts`, `patch-diff.ts` and `patch-verification.ts`, giving scoped AI patches their own enforcement surface: `SCOPE_OVERLAP`, `SCOPE_PART_LOCKED`, `SCOPE_VOLUME_EXCEEDED`, `SCOPE_REQUIRED_ATTACHMENT_MISSING` and friends. `cade85b` (00:37, 72 minutes later) closed three holes in it:

1. **Fail-open volume check.** `collectScopePolicyIssues` computed `fullPartBounds(part)`, which returns `undefined` for an unknown catalog part or an orientation not in `legalOrientationIds`. The guard read `(bounds && min-violation) || (bounds && max-violation)` — so a part with no resolvable bounds produced no issue and escaped the allowed-volume check entirely. Now it emits the new `SCOPE_BOUNDS_UNAVAILABLE` and `continue`s, with a carve-out that still permits removing such a part.
2. **Self-manufactured attachment anchor.** `scope.requiredAttachmentPorts` was only checked for "not occupied in the base". Nothing verified the port resolved on a part actually retained from the base, so a patch could delete or invent the anchor part and satisfy its own boundary condition. The fix calls `getConnectorWorldFrame(basePart, requiredPort.portId)` and emits `SCOPE_REQUIRED_ATTACHMENT_INVALID` at path `/scope/requiredAttachmentPorts/{index}` when it does not resolve.
3. **The check read the patch's claim, not the result.** Satisfaction was computed from `operations.filter(op => op.kind === "addConnection" && resultConnectionIds.has(op.connection.id))`, taking endpoints from the _operation's_ declared payload and matching the result only by connection id. A patch could add connection X touching the required port, then leave a connection with id X in the result whose endpoints no longer touched it. The fix builds `finalResultPorts` from `result.connections` directly.

`BUILD_PROGRAM_COMPILER_VERSION` went `lego.build-program-compiler/1` → `/2`; the manifest gained `scopeVolumePolicy: "authoritative-full-bounds-fail-closed/1"` and `requiredAttachmentPolicy` moved `"free-in-base-and-patch-added-surviving-edge/1"` → `"retained-base-port-and-final-surviving-edge/2"`.

**Code reviewer comments:** None recorded in the commit. The five new tests read like review findings: "rejects a required attachment manufactured entirely by the candidate", "fails closed on changed parts without authoritative bounds but permits their removal", "requires the final connection payload to preserve every required attachment port", "rejects a required attachment boundary manufactured by added parts", "pins scope hardening behavior in compiler snapshot version 2".

**Result:** +152 lines in `patch-verification.test.ts`, +74 in `compiler.test.ts`, 5 new tests, 3 closed bypasses, 2 new issue codes. Bug-to-fix interval: 72 minutes. Before the fix, an untrusted patch could place unbounded parts anywhere, invent its own attachment anchor, and satisfy the required-attachment rule with a connection payload the result did not contain.

**Reasoning:** All three are the same error in different clothes: the policy trusted something the patch controls. Bounds absence was read as bounds satisfaction; a port name was read as a port existence; an operation's declared payload was read as the document's state. The invariant "provider output cannot declare itself valid" was written in `spec.md` the same day and was still violated in code twelve hours later — a written invariant does not enforce itself.

**Validation:** Vitest over `packages/brick-kernel`. Without the change, all three tests pass a patch that the scope was supposed to reject; test 3 in particular passes a patch whose result document is missing the attachment the scope required.

**Notes:** Bumping the compiler version to `/2` is a determinism-contract change: identical inputs now hash under a different compiler snapshot, so any structural hash recorded against `/1` is not comparable. Hardening a validator is never a free change here.

## Two build-time guards that can actually fail, wired into `verify` from day one

**Timestamp:** 2026-07-09

**Action:** `b62cbdf` shipped `scripts/check-production-bundle.mjs`, which walks `apps/web/dist/` and throws if any emitted JS contains `render_app_to_text`, `capture_model_views`, `get_model_snapshot`, `advanceTime`, or `lego.app-observation/1` — and throws if the build produced no JS at all. It also shipped `scripts/check-node-consumers.mjs`, which asserts Node major >= 24, then imports every shared package under real Node and checks behavior, not presence: the generated Ajv validator must accept `positionLdu: [0,0,0]` **and reject** `[0.5,0,0]`, the catalog must load with a non-empty `PART_DEFINITIONS`, `documentStructuralHash` must match `/^sha256:[0-9a-f]{64}$/`, and `createCanonicalViewPacket` must return exactly 7 views. `build` runs the bundle guard; `verify` runs `node:check`.

**Code reviewer comments:** None recorded.

**Result:** The development automation bridge cannot silently ship to production, and the "no JS assets" case is an explicit failure rather than a vacuous pass over an empty list — the classic way a bundle guard becomes a no-op.

**Reasoning:** A guard that iterates a possibly-empty set and reports success is the exact shape of a check that cannot fail. Both scripts were written to fail on the empty and the negative case, not only on the positive one.

**Validation:** `npm run verify` and `npm run build`. Without the bundle guard, `apps/web/src/automation.ts` exposes document-reading hooks to any page in a production build.
